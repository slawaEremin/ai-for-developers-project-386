# Календарь звонков

Упрощённый сервис записи на звонок по мотивам Cal.com. Владелец создаёт типы
встреч, а гость выбирает свободное время и бронирует встречу.

Ниже описаны требования к календарю. Текущие возможности перечислены
в разделе «Разработка».

## Сценарии

### Владелец

1. Я открываю админскую часть без входа в систему: в ней по умолчанию
   используется заранее заданный профиль владельца.
2. Я создаю тип встречи «Консультация»: задаю уникальный `id`, название,
   описание и длительность в минутах — например, 30.
3. Сохраняю тип встречи. Он появляется в каталоге и становится доступен
   гостям для записи.
4. Гость выбирает свободное время и подтверждает бронирование.
5. Я открываю общий список предстоящих встреч всех типов и вижу новую запись:
   «Консультация», дата, время и длительность 30 минут.

### Гость

1. Я открываю сервис без регистрации и входа. В каталоге вижу название,
   описание и длительность каждого типа встречи.
2. Выбираю тип встречи «Консультация» и открываю календарь на ближайшие
   14 дней согласно правилам окна записи ниже.
3. Выбираю день и свободный слот, например 10:00–10:30, и подтверждаю запись.
4. Вижу подтверждение с датой и временем встречи. Запись появляется в списке
   владельца, а занятый интервал становится недоступен для других бронирований,
   включая встречи других типов.
5. Если выбранное время успели занять, вижу понятное сообщение:
   «Это время уже занято. Выберите другой слот». Новая запись не создаётся.

## Обязательные функции

- Создание типов встреч с уникальным `id`, названием, описанием
  и длительностью в минутах.
- Каталог типов встреч для гостя.
- Календарь свободных слотов в скользящем окне из 14 календарных дней.
- Бронирование свободного слота выбранного типа встречи.
- Подтверждение успешной записи.
- Общий список предстоящих встреч всех типов для владельца.
- Защита от двойного бронирования и любых пересечений интервалов,
  в том числе для разных типов встреч и одновременных запросов.
- Понятное сообщение о конфликте при попытке занять уже занятое время.

## Спецификация окна записи и занятости

- Все календарные даты и рабочие часы определяются в часовом поясе
  владельца `Europe/Moscow`. В интерфейсе часовой пояс указывается рядом
  со временем встречи.
- Окно записи начинается завтра и включает 14 календарных дней: от завтра
  до даты через 14 дней от сегодняшней включительно. Например, если сегодня
  1 июня, доступны даты со 2 по 15 июня. При смене даты окно сдвигается на день.
- Рабочие часы владельца — ежедневно с 09:00 до 18:00, включая выходные.
- Шаг доступных стартов общий для всех типов встреч — 30 минут, начиная
  с 09:00 каждого дня: 09:00, 09:30, 10:00 и так далее.
- Длительность слота равна длительности выбранного типа встречи. Слот должен
  целиком помещаться в рабочие часы: завершение ровно в 18:00 допустимо,
  позже — нет.
- Гость может создать запись только на свободный слот выбранного типа
  внутри действующего окна. При создании записи повторно проверяются окно,
  рабочие часы, шаг старта и отсутствие пересечений.
- Занятость общая для всех типов встреч. Интервалы учитываются как
  `[начало, конец)`: после записи с 10:00 до 11:00 запись с 10:30 до 11:00
  отклоняется, а запись с 11:00 допустима.
- Проверка занятости и создание записи должны гарантировать отсутствие
  пересечений при одновременных запросах. Из двух одновременных запросов
  на свободные, но пересекающиеся интервалы успешно создаёт запись только
  один; второй получает сообщение о конфликте.

## Ограничения приложения

- Владелец календаря один: его профиль задан заранее и по умолчанию
  используется в админской части.
- Авторизация, регистрация и личные кабинеты отсутствуют.
- Интеграции с внешними календарями и уведомления не входят в проект.
- Типы встреч и записи должны храниться в базе данных и сохраняться после
  перезапуска приложения и базы данных. Конкретная СУБД и способ её запуска
  определяются в спецификации.

## Технические требования

- API описывается контрактом TypeSpec. Из него генерируются OpenAPI-спецификация
  и клиентский SDK для фронтенда.
- Серверные типы, схемы проверки запросов и маршруты генерируются, если это
  поддерживает выбранный фреймворк. Если подходящего серверного генератора нет,
  сервер реализуется по контракту, а соответствие проверяется тестами.
- Приложение должно собираться в Docker-образ и запускаться в контейнере.

Источник требований: [первый шаг проекта Hexlet](https://ru.hexlet.io/projects/386/members/52904?step=1).

## Разработка

Проект построен на FastAPI, Vue, TypeScript и TypeSpec. Реализованы создание
типов встреч, каталог с прямыми ссылками, календарь на 14 дней, подтверждение
записи, восстановление незавершённой попытки и список предстоящих встреч
владельца. Регистрация и данные гостя не требуются. PostgreSQL хранит типы,
записи и успешные ключи попыток; транзакции и ограничение БД защищают общую
занятость от пересечений.

Нужны Docker с Compose, Node.js 24.22.2, npm 10.8.2 и uv 0.13.7. Версии
закреплены в `.nvmrc`, `package.json` и `apps/backend/pyproject.toml`;
uv устанавливает Python 3.13.18 из `apps/backend/.python-version`.

Самый короткий путь запуска:

```sh
docker compose up --build
```

Откройте [главную](http://127.0.0.1:8000/),
[страницу владельца](http://127.0.0.1:8000/#/owner) или
[запись гостя](http://127.0.0.1:8000/#/booking).
При первой подготовке создаётся один владелец и пустой календарь. Перед
запуском сервера отдельная команда применяет версионируемые миграции;
ошибка подготовки останавливает запуск. Именованный том сохраняет данные
при `docker compose down` и пересоздании контейнеров. Повторная подготовка
не заменяет владельца и не очищает календарь.

Для локальной разработки запустите PostgreSQL и установите зависимости:

```sh
docker compose up -d db
npm install --global "$(node --print "require('./package.json').packageManager")"
make setup
make check
```

При использовании nvm предварительно выполните `nvm install` и `nvm use`.
Команды Make работают из корня и через `make -C /путь/к/репозиторию`.

| Команда | Действие |
| --- | --- |
| `make setup` | Установить зависимости из lock-файлов и сгенерировать контракт, модели и SDK |
| `make generate` | Обновить OpenAPI, Pydantic-модели и TypeScript SDK |
| `make lint` | Проверить Python, Vue, TypeScript, TypeSpec и актуальность генерации |
| `make test` | Выполнить HTTP-тесты с PostgreSQL и DOM-тесты без watch-режима |
| `make build` / `npm run build` | Проверить типы и собрать фронтенд |
| `make check` | Последовательно выполнить lint, test и build |

HTTP-тесты используют настоящую БД и отдельные временные схемы, сохраняя
рабочие данные. Другой сервер PostgreSQL можно задать через
`TEST_DATABASE_URL`; подключение приложения задаётся `DATABASE_URL`.
Сквозной браузерный сценарий и команды его запуска описаны в
[README фронтенда](apps/frontend/README.md).

Бэкенд и фронтенд для разработки запускаются в отдельных терминалах:

```sh
cd apps/backend
uv run --locked python -m app.prepare
uv run --locked uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

```sh
npm run dev --workspace apps/frontend
```

Vite доступен по адресу `http://127.0.0.1:5173/` и проксирует API на бэкенд.
`GET http://127.0.0.1:8000/health` возвращает `{"status":"ok"}`;
Swagger UI доступен по адресу `http://127.0.0.1:8000/docs`.
Все календарные ответы `/api/*` используют JSON и `Cache-Control: no-store`.

В Docker FastAPI отдаёт API и собранные ресурсы Vue одним процессом Uvicorn.
Подробнее: [бэкенд](apps/backend/README.md),
[фронтенд](apps/frontend/README.md), [контракт](specs/README.md),
[Docker и сохранность данных](apps/infra/README.md).
