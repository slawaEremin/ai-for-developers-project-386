# Бэкенд

FastAPI и Uvicorn работают на Python 3.13.18 из `.python-version`.
Зависимости закреплены в `uv.lock`; окружением управляет uv 0.13.7.

Из корня выполните `make setup` и запустите PostgreSQL. Затем отдельно
подготовьте БД и запустите сервер:

```sh
docker compose up -d db
cd apps/backend
uv run --locked python -m app.prepare
uv run --locked uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

По умолчанию `DATABASE_URL` — `postgresql://calendar:calendar@127.0.0.1:55431/calendar`.
`OWNER_NAME` задаёт имя при первом создании единственного владельца;
по умолчанию «Владелец календаря». Подготовка применяет SQL-миграции
из `app/migrations` и создаёт только отсутствующего владельца. Повторный запуск
не заменяет владельца и не очищает данные. Новые изменения схемы добавляйте
отдельной нумерованной миграцией, сохраняя уже применённые файлы.

`python -m app.start` запускает подготовку отдельной командой и только после
её успеха заменяет процесс одним Uvicorn worker. Эта команда используется
в контейнере; ошибка подключения или миграции предотвращает старт HTTP-сервера.
При недоступной БД работающий API возвращает 503, без хранения в памяти.

Реализованы `GET /health` с ответом `{"status":"ok"}` и
`POST /api/meeting-types` с ответом 201. Тип сохраняется в PostgreSQL. `GET /api/meeting-types` возвращает
`serverTime` в UTC и `items` с полными типами (пустой каталог — пустой массив).
Порядок — название, затем id, по кодовым точкам Unicode с учётом регистра.
`GET /api/meeting-types/{id}` возвращает один тип без оболочки:
неправильный формат id даёт 422, отсутствующий корректный id — 404
с кодом `MEETING_TYPE_NOT_FOUND`.
Повторный id даёт 409, некорректные поля — 422, JSON — 400,
неподдерживаемый Content-Type — 415. Ошибки имеют `code`, `message`
и при необходимости `fieldErrors`; ответы `/api/*` имеют `Cache-Control: no-store`.
`GET /api/meeting-types/{id}/availability` возвращает ровно 14 дат: завтра
и следующие 13 дней в Europe/Moscow. От одного `clock_timestamp()` PostgreSQL
вычисляются `serverTime`, включительные `windowStartDate`/`windowEndDate`.
Каждый день содержит `date` и `slots` с UTC-интервалами `startsAt`/`endsAt`
(суффикс Z). Рабочие часы ежедневно 09:00–18:00, сетка стартов 30 минут;
длительность не округляется. Пустые дни сохраняются. Все записи таблицы
`bookings` создают общую занятость независимо от типа; полуоткрытые интервалы
могут соприкасаться. Миграция `002_bookings.sql` вводит хранимые интервалы
и ограничение PostgreSQL против пересечений.
`POST /api/bookings` принимает только `meetingTypeId` и `startsAt` (RFC 3339
с `Z` или явным смещением), требует UUID в `Idempotency-Key`.
Новая запись возвращается с 201, успешный повтор тех же данных — 200 с прежним id.
Эквивалентные смещения равнозначны, изменённые данные по успешному ключу дают
409 `IDEMPOTENCY_KEY_REUSED`. Успешные ключи хранятся в `booking_keys`
(миграция `003_booking_keys.sql`) атомарно с записью. Отказы ключ не занимают.
Создание явно использует Read Committed: блокирует единственную строку владельца,
свежим отдельным запросом проверяет успешный ключ, затем один раз получает время
БД и проверяет окно, часы, сетку и общую занятость. Блокировка удерживается
до COMMIT; ответ об успехе отправляется после него. Пересечение даёт
409 `SLOT_CONFLICT`, выход за окно — 422 `OUTSIDE_BOOKING_WINDOW`,
нарушение сетки/часов — 422 `INVALID_SLOT`.
Для управляемых проверок времени сценария используется зависимость
`app.clock.calendar_clock`; производственная реализация читает время БД.

Swagger UI: `http://127.0.0.1:8000/docs`.

```sh
uv run --locked pytest
uv run --locked ruff check .
uv run --locked ruff format --check .
```

HTTP-тестам нужен настоящий PostgreSQL. `TEST_DATABASE_URL` выбирает сервер
(по умолчанию тот же локальный адрес). Каждая проверка создаёт уникальную
схему `calendar_test_<uuid>`, использует её через `search_path` и удаляет только
эту схему; данные приложения не очищаются. Нужны права создания схем.
При отсутствии БД тесты завершаются ошибкой, а не пропускаются.
В CI используется отдельная БД `calendar_test` сервиса PostgreSQL.

Модели `app/generated/models.py` генерируются из TypeSpec командой
`make generate`; вручную их не меняйте. FastAPI отдаёт фронтенд из `dist`
или каталога `STATIC_DIR`, если он существует.

Для подтверждения действует один абсолютный бюджет 10 секунд: подключение,
ожидание блокировки, все SQL-команды и COMMIT. При остатке меньше минимальных
двух секунд libpq новое подключение не начинается. PostgreSQL 40P01/40001
повторяют всю транзакцию с новым соединением, максимум три выполнения всего;
остальные технические ошибки автоматически не повторяются. Время ожидания
сокета и statement_timeout ограничены остатком бюджета, в том числе на COMMIT.
Исчерпание даёт 503 SERVICE_UNAVAILABLE. Если ожидание COMMIT прекращено,
сервер не утверждает, что записи нет: явный повтор с тем же ключом безопасно
возвращает прежнюю запись или выполняет новую проверку, если был rollback.

`GET /api/bookings/upcoming` возвращает `serverTime` и общий `items` всех типов.
Время БД захватывается один раз при загрузке; включаются начала `startsAt >= serverTime`,
в том числе точное равенство. Уже начавшиеся встречи исключены до их окончания.
Гостевое окно не ограничивает список; порядок — начало, затем UUID, без пагинации.
Пустой список — 200 с `items: []`. Объекты совпадают с ответом подтверждения;
ответы и ошибки имеют `Cache-Control: no-store`. История и успешные ключи
не удаляются при чтении списка или повторной подготовке БД.
