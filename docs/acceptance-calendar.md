# Приёмка календаря звонков

Реализация спецификации [#10](https://github.com/slawaEremin/ai-for-developers-project-386/issues/10)
и задач #11–#16. Номера ниже соответствуют согласованной
[матрице из 40 критериев](https://github.com/slawaEremin/ai-for-developers-project-386/issues/8#issuecomment-6809555409).

Проверки HTTP используют настоящую PostgreSQL и отдельную временную схему
на тест. Рабочие таблицы приложения не очищаются. DOM-тесты проходят через
пользовательские действия и сгенерированный SDK с управляемой HTTP-границей.
Время задаётся на общей границе календарного сценария; в рабочем приложении
источником остаётся `clock_timestamp()` БД.

Для краткости в таблице используются следующие обозначения файлов:

- **Типы** — [test_meeting_types.py](../apps/backend/tests/test_meeting_types.py).
- **Доступность** — [test_availability.py](../apps/backend/tests/test_availability.py).
- **Запись** — [test_bookings.py](../apps/backend/tests/test_bookings.py).
- **Предстоящие** — [test_upcoming.py](../apps/backend/tests/test_upcoming.py).
- **Форма** — [owner.test.ts](../apps/frontend/tests/owner.test.ts).

- **Список** — [upcoming.test.ts](../apps/frontend/tests/upcoming.test.ts).

## Воспроизведение

Установите зависимости по корневому README и запустите PostgreSQL.
`make lint`, `make check` и `npm run build` проверяют код, генерацию,
HTTP/DOM-сценарии и production-сборку. Команда браузерного теста и его
изолированная БД описаны в [README фронтенда](../apps/frontend/README.md).
Порядок запуска Compose и требования к сохранности — в
[README инфраструктуры](../apps/infra/README.md).

## Проверка запуска

Итоговый прогон выполнен 12 ноября 2026 года на Node.js 24.22.2,
npm 10.8.2, Python 3.13.18 и настоящем PostgreSQL 17.

- `make lint` и `make check` прошли. После исправлений ревью — 122 серверных
  HTTP/PG-теста и 41 DOM-тест; генерация, проверка типов и production-сборка актуальны.
- В TCP-прокси теста общего deadline нормальное закрытие клиента учитывает
  EOF и TCP reset на разных ОС; проверки времени, 503 и отсутствия записи
  остаются обязательными.
- `npm run build` прошёл. `E2E_BROWSER_CHANNEL=chrome npm run test:e2e` прошёл:
  один настоящий браузерный сценарий через production Vue, SDK, FastAPI и БД.
  Часовой пояс браузера — America/Los_Angeles, отображение — московское.
- Оба замечания Standards о дублировании устранены общей календарной политикой
  и московскими форматтерами. Spec-ревью не нашло подтверждённых нарушений.
  Дополнительно исправлена и проверена навигация из pending/unknown состояния;
  настоящий HTTP500 проверяет JSON/no-store и отсутствие частичного сохранения.

Compose запускался отдельным проектом `calendar-spec10` с новым томом
`calendar-spec10_calendar-data`. Временный override изменял только порты:
приложение `127.0.0.1:18010`, БД `127.0.0.1:55432`.

1. `docker compose ... up --build -d --wait` собрал и запустил приложение и БД.
   Первая выдача каталога и предстоящих — пустые массивы.
2. HTML и фактические JS/CSS вернули 200; `/health` — 200 и `status: ok`.
   Созданы типы на 45 и 30 минут; доступность содержит ровно 14 московских дат.
3. Запись создана с 201, повтор с исходным ключом — 200 и тот же UUID.
   Запись другого типа на пересекающееся время получила 409 SLOT_CONFLICT;
   интервал исчез из общей доступности. Список владельца содержит одну запись.
   Ответы календарного API — JSON с `Cache-Control: no-store`.
4. Повторная `python -m app.prepare` с другим OWNER_NAME сохранила исходного
   владельца, оба типа, запись и ключ. Это подтверждено SQL и повтором через API.
5. Остановка БД привела к 503 SERVICE_UNAVAILABLE для календарного API;
   `/health` сохранил свой контракт. Ложного подтверждения не было.
6. После запуска БД и перезапуска приложения прежние типы, запись и ключ
   доступны. После ожидания готовности HTTP повтор вернул тот же UUID.
7. Окончательный образ с исправлениями ревью пересобран; команда
   `up --build -d --wait --force-recreate db app` пересоздала оба контейнера
   с прежним томом. После готовности HTTP запись по исходному ключу вернулась
   с 200 и первоначальным UUID. HTML и новые JS/CSS также вернули 200.
8. Запуск образа с недоступным DATABASE_URL завершился ненулевым кодом
   на подготовке БД и записал OperationalError; Uvicorn не запускался.
9. `docker top` подтвердил непривилегированного пользователя и один процесс
   Uvicorn с `--workers 1`. Мобильные страницы владельца и гостя на ширине
   390 px не имеют горизонтального переполнения.
10. Временные контейнеры, сеть и тестовые тома удалены после проверки.
    Рабочие данные пользователя не очищались.
